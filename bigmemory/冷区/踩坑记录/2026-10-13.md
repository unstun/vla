# Newton v47–v188 pitfalls: repository state, controls, Foxy bring-up, recovery and evidence

Archived 2026-10-13 07:05 America/Los_Angeles. Stage: experiment + analysis. Trellis task `09-23-scan-reactive-stair-pedestrian` and its `10-02-newton-*` / `10-04-newton-*` subtasks. Paths are relative to `.pipeline/experiments/2026-09-26_newton_stair_reproduction/` unless absolute. "原因" lists only verified causes; where a cause is unproven, the entry says so. Commit: none at write time.

## 1. A stale `.git/index.lock` silently blocked every commit after 2026-10-01

- 现象: v47–v188 (Oct 2–13) were never committed. The last commit is 943d0a9bb (2026-10-01 01:34 PDT).
- 原因 (verified on 2026-10-13 by the archive session, re-checked read-only at 07:05): an empty `.git/index.lock` dated 2026-10-01 02:46, with no git process running. Git refuses to stage or commit while this file exists.
- Also: 10 `tmp_pack_*` files (2.06 GiB, dated 09-30..10-04) in `.git/objects/pack` are leftovers of unfinished pack writes. Which commands left them is not known.
- 处理: the archive session removed the 0-byte lock on 2026-10-13 after `pgrep` showed only read-only git processes (an app status poll with `--no-optional-locks` and a check-ignore in machine-dog). The tmp_pack files were left in place; cleaning them (`git gc`/`git prune`) waits for Dr Sun.
- 未来用途: if commits stop appearing, or `git add` reports an `index.lock` error, look for a stale lock first. Check git state at the end of every long session so a blocked repository is noticed within a day, not twelve.

## 2. An unchanged rebuild failed as often as the candidates: always run an unchanged control

- 现象: the terminal-capture candidates v185 (3/5), v186 (2/5) and v187 (3/5) looked like regressions from v177's 5/5.
- 原因 (verified): v188 rebuilt all 649 native sources unchanged (ELF `.text`, `.dynstr` and `.data.rel.ro` identical; `.rodata` differing only in 24 path bytes) and still arrived only 3/5. The existing v177 binary cohort (attempts 06–10) arrived 5/5. So some failures happen without any new logic, and the cause of the variation is unknown. An earlier sign: in the v127 follow-up, the unchanged parent v122 arrived 0/6 (one fall), though it had arrived earlier on the same host.
- 未来用途: five runs cannot separate a change's effect from run-to-run variation. Never credit or blame a change without a contemporaneous unchanged control, never pool cohorts, and never call v177's 5/5 "stable". `versions/v188/RESULTS.md`, `audits/2026-10-10_mppi_step3_repeats/REPORT.md`.

## 3. v59: a retry chain relabeled an old sample with a later timestamp

- 现象: one v59 round made eight rebound attempts and took 1.237 s, followed by a 1.099 s measured hold.
- 原因 (verified by the cold-recovery audit): each `reboundReplan()` call checked again whether the old curve was still unexpired. Once it expired during the earlier failed attempts, the call dropped the known sample epoch, so the unchanged PVA sampled at 81.027 s was published with an origin of 82.286 s (a 1.259 s shift). Separately, rebound repair kept going after a failed initialization (3 searches in the fixture where 1 was enough).
- 处理: v62 carries the timestamp through the chain, bringing the shift from 1.259 s to 0. v63 returns the failure. Both are Mac component tests only.
- 未来用途: delayed single-call tests passed and missed this defect. Any time-origin change needs a regression in which retries cross the old curve's expiry. `audits/2026-10-03_v59_cold_recovery/REPORT.md`, `versions/v62/RESULTS.md`.

## 4. A new failure reason must be tested through its real consumer

- 现象: v49 sent 80 stop commands, kept restarting planning, and made only 1.432 m of progress.
- 原因 (verified against the exact frozen handler AST, `versions/v49/analysis/check_stop_protocol.py`): the new FSM emits `native_solve_timeout`, but the unchanged backend closes the owner gate only for `native_replan_exhausted`. The new reason was simply ignored.
- 未来用途: before physics, run every new stop/timeout/failure reason through the real backend handler and terminal stop flow. §11 is the same class of bug.

## 5. Foxy/ARM64 bring-up (v92–v98): each fix exposed the next blocker

- 原因 (each verified in its own run; `audits/2026-10-08_nav2_full/REPORT.zh.md`):
  - Environment: the old ZeroMQ package was built for x86 / Python 3.10 and does not work on ARM64 Foxy (v92). System NumPy 1.17 lacks an interface the original terrain helper uses (v93); v94 isolates NumPy 1.24.4, and the three terrain payloads come out byte-identical.
  - Timing: the sensor's JIT compile on its first scan took longer than the 0.1 s sensor period, so physics stopped (v94); v95 compiles before timed sensing starts. Foxy's default BT action-ack wait (about 10 ms) timed out the goal (v95); v96 sets 1000 ms explicitly, as a transport window rather than a safety limit.
  - Protocol: a repeated cancel before the first spline missed its acknowledgment (v96; fixed in v97). Float time conversion judged a body stamp from the same nanosecond to be in the future (v97); v98 moves to canonical integer ROS time.
- 未来用途: a Jetson (ARM64 Foxy) bring-up will likely hit the same issues. Prepare architecture-specific wheels, a NumPy pin, JIT warm-up before timing, explicit action-ack timeouts and integer time arithmetic in advance.

## 6. Foxy's `/clock` subscription sits in the default callback group

- 现象: body messages were rejected as "future" because the node clock lagged behind the real body samples.
- 原因 (verified by recorded replay; future-body rejections fell from 27/27 to 0/27 once the clock had its own lane): Foxy's TimeSource subscribes to `/clock` in the default callback group. A long single-threaded native callback therefore blocked clock updates, while manual DDS takes kept pulling in newer body data.
- 处理: v100 runs a two-thread executor with an exclusive work group; v101 admits a body message only once it is due.
- 未来用途: a separate clock lane does not guarantee message order across topics, and v100 still failed for that reason. `audits/2026-10-08_nav2_sim_repair/DIAGNOSIS.md`.

## 7. A coarse height map hid a real floor seam (v133)

- 现象: in `v133_candidate_attempt02`, PD rejoin began at 36.731 s after an upright stop. The left-front foot slipped into a seam, body tilt grew from 1.6° to 29.3°, and the final stillness check never completed.
- 原因 (verified from recorded transforms and the original static triangles): the Building mesh contains a seam about 7 cm wide, but the 10 cm PCT cell reports ground at about 4.533 m across it. A sampled maximum height does not mean the whole cell can support a foot.
- 处理: v134 adds negative static support coverage, and v135 couples PCT costs to the same veto; v139 then passes the declared scenario.
- 未来用途: the fix stops the robot from entering this unsupported pose. It cannot get the robot out of one, and waiting longer or retrying more cannot create floor. Other maps need their own seam audit. `audits/2026-10-10_v133_posture/REPORT.md`.

## 8. A collision-sample grid anchored at the interval start missed a narrow voxel (v150)

- 现象: on curve 2366, the full interval checked clear, but the remaining interval checked 24.99 ms later was blocked.
- 原因 (verified on the unchanged native v147 library): a narrow UnknownObstacle voxel fell between the samples of the first grid. It was hit only after `begin_s` shifted the grid.
- 处理: v151 keeps every original sample and adds 4 interior samples per interval.
- Terminology correction: native enum 6 is `UnknownObstacle`, and the logged `support_z` is the adjusted query height, so the earlier "support-clearance" label was wrong.
- 未来用途: a clear-then-blocked flip can come from sampling, not from a map change. Read verdict enums from the source before labelling a failure. v151's shared sample count also raises warm-seed sampling; that coupling is still unresolved. `versions/v150/RESULTS.md`.

## 9. Mac Docker ACK latency outran a 3 × 100 ms wait (v167)

- 现象: v167 Mac full01 stopped at 48.145 s sim time. Copyback was unqualified because the host had ACKed sequence 1856 while the receiver already had 1857.
- 原因 (verified from Linux receipts): the receiver committed 1857 after 353 ms, but the client gave up after 3 × 100 ms. There was no native failure.
- 处理: v169 keeps 3 idempotent attempts and the 100 ms send timeout, but waits up to 400 ms per receive. It adds no timestamp refresh and no infinite retry.
- 未来用途: count runs like this as infrastructure failures, never as arrivals or recovery evidence. `versions/v167/RESULTS.md`, `versions/v169/PLAN.md`.

## 10. The Nav2 recovery budget is shared by the whole mission (v169)

- 现象: v169 travelled 74.06 m with six qualified handoffs, then the seventh stop aborted the whole mission.
- 原因 (verified): FoxyRecoveryNode keeps its six retries until the primary child succeeds at the final goal. Stops at different places along a long route all draw on the same budget.
- 处理: v170 renews the budget on measured spatial progress. A larger fixed cap (v131) was tried and not adopted.

## 11. An arrival does not prove the new branch ran (v170)

- 原因 (verified): Newton's frame is `base`, but the BT default was `base_link`, so v170's renewal branch never fired. Its arrival fit inside the old budget. Once v172 carried the frame through, renewal fired 4 times in v172 and 4 times in v174.
- 未来用途: credit a new branch only when its event appears in the logs, and check frame names inside the generated BT XML. `versions/v170/RESULTS.md`.

## 12. PCT aborted on a singleton A* path near the goal (v172)

- 原因 (verified by reproducing the captured native abort): a degenerate single-point query aborted the PCT process, and every later RPC failed. The first, guard-only fix then exposed stale A* search state left after an empty query.
- 处理: v174 rejects short queries without aborting and resets every search.
- 未来用途: test an empty query followed by a full query, not each one alone. `versions/v172/RESULTS.md`, `versions/v174/RESULTS.md`.

## 13. The 15 cm local-spline finish radius acted as a deadband (v176)

- 原因 (verified by a recorded tracker counterfactual): with a 15 cm radius, the tracker outputs zero at a 4.9246 cm endpoint error. With 2 cm, it issues an inward correction. A 1 cm error still stops.
- 未来用途: v177's 5/5 rests on this single parameter. The later endpoint changes (v184–v187) changed crawl behavior without improving arrivals. v186 also showed that a 1 s / 5 mm progress watcher does not bound duration: small measured motion stretched one crawl to 5.477 s. `versions/v176/RESULTS.md`, `versions/v186/RESULTS.md`.

## 14. 5/5 arrivals did not validate stop retention (v177 audit)

- 现象: in run01, for about 15.86 s, all 661 upper-level commands were zero, as were the effective commands in 783 low-level telemetry records. The body still drifted about 0.957 m. It stayed in STAND_SETTLING and never reached a fixed stance, mainly because the four-foot contact condition blocked it.
- Related: 20 of the 35 revocations used safety data 252–275 ms old, past the 250 ms gate, even though a side observer already held a newer frame. The logs cannot separate input, compute and lock waits, so no cause is attributed for this delay.
- 未来用途: report stop retention separately from arrival. Map-data expiry is the largest revocation class. `audits/2026-10-12_v177_stop_causes/REPORT.zh.md`.

## 15. Tests below operating speed made the policy look unable to stop (v179)

- 原因 (verified in v182): every v179 command (0.2/0.35/0.5 m/s) was below the project's 0.6 m/s planned-cruise rule. At 0.6/0.8/1.0 m/s, late-excursion flags over 5 cm fell from 4 to 0 on flat ground and from 7 to 4 on stairs. The proposed standing-takeover and training remedies were premature.
- 未来用途: test the policy inside the speed range navigation actually commands before diagnosing it. The RL input audit shows that the small end-of-curve commands come from the navigation controller itself. `versions/v182/RESULTS.md`.

## 16. Raw evidence kept under `/private/tmp` disappeared twice

- 现象: the v74 temporary raw root was gone after an interruption. When work resumed on 10-12, the v149 owned root `/private/tmp/vla_newton_v149_j338wipj` was missing, together with its Mac raw captures, native installs and Linux fixture. This superseded the earlier "complete raw retention" statements.
- 原因: not established; no task issued a cleanup.
- 处理: v76 archives raw data durably right away; v154 restored the native build from the local frozen source.
- 未来用途: copy raw data to durable storage (the gpu5070ti archive) as soon as each trial closes. A retention claim needs a durable hash, as AGENTS.md already requires. `versions/v74/RESULTS.md`, `versions/v154/RESULTS.md`.

## 17. Launchers refused frozen versions on metadata

- 原因 (verified in each version): an inherited floor-publisher environment key (v71); the launcher expected the old all-packages build key (v104); a metadata admission failure (v153); the frozen quality metadata lacked a required package count (v184).
- 未来用途: dry-run launcher admission against the frozen metadata before calling a version ready. These refusals are infrastructure failures, not navigation evidence.
- Related measurement note: the same v147 run has a 76.883 m sensor-rate path and a 77.945 m video-state path, so compare path lengths only at the same sample rate.
