# HarnessVLN Direction And Evidence Boundaries

Archived at 2026-09-16 21:32 America/Los_Angeles. Stage: experiment + analysis.
Task: `09-16-emos-harnessvln-reimplementation`.

## Decisions And Reasons

Dr Sun selected Pi plus Cortex/EMOS-compatible tools to reimplement supportable
HarnessVLN mechanisms, then chose the existing Isaac Lab / Lite3 / native
PCT-SCAN stack because it provides the intended path toward real deployment.
This supersedes the earlier Habitat-first implementation proposal. The design
keeps the Pi decision loop, semantic task/evidence handling, navigation service
and locomotion execution separate so their claims can be tested independently.
The current compatible gateway is not an actual Cortex runtime, and eventual
physical deployment is a goal, not current authorization or readiness.
Sources: [design](../../../.trellis/tasks/09-16-emos-harnessvln-reimplementation/design.md)
and [task state](../../../.trellis/tasks/09-16-emos-harnessvln-reimplementation/task.json).

The first real navigation slice used a fixed known map and simulator truth
poses to establish continuous goal/cancel/stop/replan behavior before adding
vision-language uncertainty. Actual4 passed, but three subsequent display
probes failed A resubmission. Both facts are retained: the earlier result is a
valid single pilot, while general interruption/recovery reliability remains
open. Fixture protocol checks, a simulator episode and a language-driven
HarnessVLN evaluation are different evidence scopes.
Sources: [P2B acceptance](../../../.pipeline/experiments/2026-09-16_pi_cortex_harnessvln/P2B_RESULT.md)
and [subsequent display probes](../../../.pipeline/experiments/2026-09-16_pi_cortex_harnessvln/pointcloud_display/RESULT.md).

Dr Sun requested more GPU use during live point-cloud testing. The chosen
profile uses actual NVIDIA RViz rendering and NVENC recording, with latest-only
clouds and a bounded display rate. It is now the display wrapper default.
Success is based on the observed renderer, encoder, decoded media and resource
samples, not on requesting a GPU flag. The short run was deliberately reported
as display plus capture overhead rather than an isolated rendering benchmark.
Source: [display evidence and limitations](../../../.pipeline/experiments/2026-09-16_pi_cortex_harnessvln/pointcloud_display/RESULT.md).

The failed restart was investigated at the native planner boundary because it
also occurred with display disabled. A fresh-manager, empty-map native replay
removed cancellation timing and GPU workload as necessary causes for the
observed candidate rejection. A one-variable endpoint-derivative change then
separated the identified mechanism from parameter tuning. Existing motion
limits and timeout checks were retained. The candidate is left isolated until
endpoint/collision behavior and continuous Isaac execution are checked.
Sources: [diagnostic plan](../../../.pipeline/experiments/2026-09-16_pi_cortex_harnessvln/scan_replan_diagnosis/PLAN.md),
[result](../../../.pipeline/experiments/2026-09-16_pi_cortex_harnessvln/scan_replan_diagnosis/RESULT.md)
and [independent review](../../../.pipeline/experiments/2026-09-16_pi_cortex_harnessvln/scan_replan_diagnosis/independent_review.json).
