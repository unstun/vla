Lite3 四足机器狗 · 楼宇（含楼梯）自主导航算法架构

这页把目前仿真里在跑的整条导航链路，从“给一个目标点”一直到“四条腿怎么动、怎么停稳”，按层讲清楚。每一层先用人话说它干什么，再给出真实参数、源码位置和已知失败。

所有数字来自本地仓库的冻结源码和审计报告；没有核实过的内容会明确标注。

已采纳单路线基线：v232 源码 / v233 执行 最新版本 v288：未通过验收（10 条中 1 条到达） 仅仿真（Newton），无真机运动 VLA 尚未接入闭环

一页总结

一句话：机器狗靠“分层”导航——上层 Nav2 管任务和重试，PCT 在整栋楼的多层地图上画出一条全局路线，SCAN 每秒约 30 次根据激光雷达实时建的三维地图，把前方 3.5 m 内的路线优化成一条平滑、不撞墙、踩得到台阶的 B 样条轨迹；跟踪器把轨迹换算成速度指令，交给强化学习（RL）步态策略驱动四条腿；到终点后切换到关节 PD 站立保持不动。

它擅长什么
原始那一条楼梯路线已在 v233/v237/v241 各单次完整走通：约 121–124 s 到达，PD 站稳约 4.4 s，终点误差约 12–14 cm。
它还不行的
换起终点（泛化）不稳：最近 7 个版本在固定 10 条路线上“到达+站稳+几何全程不越界”只有 0–5 条。
v288 的新问题
入口锁引起位姿时间戳倒序，并被永久锁死（6 条），终点 2 cm 居中条件过严导致超时（2 条）。

从上往下看是“指令流”（目标 → 路线 → 轨迹 → 速度 → 关节），右侧向上的虚线是“感知流”（仿真世界 → 雷达点云 / 机身位姿 → 三维地图）。点击任意方块可以跳到对应章节。

一次导航的完整过程（按时间顺序）

  1. 开机起立。仿真中机器狗先按出厂流程“趴 → 回零 → 准备 → 站起”，当四只脚受力达标后，由关节 PD 接管保持站立（factory_navigation_startup.py，最长等 14 s）。这一段单独审计，不算导航。
  2. 下发目标。外部通过 HTTP 把终点 XYZ + 朝向发给 MissionBridge（默认 127.0.0.1:8785），它转成 Nav2 标准动作 NavigateToPose，并记录任务身份，防止旧任务的回复串进来。
  3. 算全局路线。行为树调用 ComputePathToPose(planner_id=PCT)。PCT 在整栋楼的多层“断层图”上搜索，输出一条带高度的路线（跨楼梯）。离线门禁要求合法例的全局算路中位耗时 ≤ 1.5 s。
  4. 把路线绑给 SCAN。行为树执行 FollowPathWithFailure(controller_id=SCAN)。必须先拿到 SCAN 的“路线绑定确认”，才允许开始跟随；一个任务只保留一个全局路线“纪元”（epoch），不会中途被换掉。
  5. 一边走一边建图。雷达每 0.1 s 出一帧点云，SCAN 把它融合进 0.05 m 分辨率的三维占据栅格（滑动窗口跟着机器狗走），同时结合离线的“哪里能踩”支撑图判断每个位置是否可通行。
  6. 每秒约 30 次重规划。状态机按墙钟 30 Hz 触发重规划（预算 33.3 ms）：取全局路线前方约 3.5 m 处作为局部目标，生成种子路径 → 拟合 B 样条 → 用 L-BFGS 把曲线“推离”障碍并保持平滑 → 调时间满足速度/加速度 → 用最新地图把整条曲线逐点再查一遍，查过了才发布。
  7. 跟踪轨迹。Controller Server 以 30 Hz 采样当前轨迹，跟踪器算出 [vx, vy, ωz]，经过限幅/斜率限制/命令门禁后送给 RL 步态策略。若 0.75 s 内拿不到可执行轨迹，判 “Native SCAN has no executable trajectory”，交回行为树恢复。
  8. 出问题时恢复。行为树先要“实测停稳证明”（连续 1 s：指令范数 < 0.01、水平速度 < 0.1 m/s、偏航角速度 < 0.15 rad/s），再等 1 s 重试；整个任务最多重试 6 次。
  9. 进入终点圈。距离终点 XY ≤ 0.25 m、高度 ≤ 0.20 m 时，跟踪器冻结轨迹进度，开始终点收尾（对准最终朝向；v288 还加了往中心挪的逻辑）。
  10. 站稳、完成。朝向和位置达标、指令归零后，交给 PD 站立保持（配置 stand_hold_seconds: 2.0，最长 10 s），实测站稳后任务记为 FINISHED。

① 物理仿真与雷达

Newton 物理仿真 + Livox MID-360 几何雷达

仿真世界
人话：这是“假世界”。它模拟楼、楼梯、机器狗的身体和地面接触，并按真实 MID-360 雷达的扫描花样往外打射线，生成点云。导航算法只能看到点云和机身位姿，看不到“答案”。
物理引擎
Newton（GPU/CPU 可选；正式实跑 CPU BVH 射线）
物理步频
约 1 kHz（由实跑步数/时长推算，例如 A04：69 780 步 / 69.75 s）
场景
Building 楼宇网格（含楼梯、走廊、柱子）；起终点来自 50+3 冻结队列
雷达模型
官方 MID-360 扫描模式 inputs/livox_mid360/mid360.csv；只排除雷达自身外壳的自回波，机身其它部分保留
雷达时序
周期 0.1 s，单帧截止 0.1 s；v288 全部 4 620 帧 0 次超时
执行主机
ultra9（v286 起）；早期 gpu5070ti；gpu40901 迁移有单独失败记录
技术细节：为什么雷达时序是硬门禁

v235 在 gpu40901 上首次实跑就卡在“扫描截止”守卫（12.8 s 停）；v236 修复了原生时钟提前拒绝与固定核调度问题，之后 0.1 s 截止一直保持不变。雷达帧如果晚到，地图就是“旧的”，后面所有安全检查都会失真，所以项目规则是绝不放宽 0.1 s，只能修调度。

源码：scripts/geometric_lidar.py、scripts/robot_scene.py、scripts/newton_episode.py（v288 通过 versions/v288/newton_episode.py 复用 v241/v237 冻结版本，只改执行身份）。

② 机器狗身体：RL 步态 + PD 站立

强化学习行走策略 + 关节 PD 保持

身体层
人话：导航只告诉狗“往前多快、往侧面多快、转多快”。怎么迈腿由一个训练好的神经网络（RL 策略）决定；停下时换成更稳的“关节弹簧”（PD）把姿势锁住。
行走策略
冻结 v216 RL locomotion 策略（来自 sibling 仓库 machine-dog 的训练链路）；导航版本迭代中从未改动
输入
机体系速度指令 [vx, vy, ωz]；控制器上限 vx 1.0 m/s、vy 0.35 m/s、ωz 1.0 rad/s
站立保持
起立后、终点停稳后由关节 PD 接管；状态 RL → STAND_SETTLING → STAND_TRANSITION → FIXED_STAND，任何非零指令触发 REJOIN 回到 RL
终点要求
实测 PD 保持（v233 基线 4.398 s）；失败路线不计
技术细节：为什么步态会影响终点

RL 步态即使指令很小也会踏步，机身有厘米级的晃动和静差。v287 在终点“原地纯转向”时，机身实际朝向与曲线切向可差 100° 以上，屁股扫到墙（D07 −1.64 cm、CD12 −4.23 cm）。v288 想用“边转边往中心挪 + 2 cm 才算到”解决，却碰上了踏步晃动本身就有 2–5 cm，导致 S04/CS03 在终点附近超时。

术语见 .pipeline/terminology/terminology.md 中的 stance hold、terminal crawl。

⑤ SCAN 三维地图与可通行判定

GridMap（plan_env）

局部层
人话：机器狗身边一个 10 m × 10 m × 5 m 的“乐高积木盒”，每块积木 5 cm。雷达打到的地方标“有东西”，射线穿过的地方标“空”。再结合离线的“哪里能踩”信息，回答一个问题：狗的身体放在这个位置、这个朝向，安全吗？

“这里能不能放身体”的判定

  1. 机身足迹：双圆柱模型，double_cylinder_radius = 0.35 m（即项目的 0.35 m 硬阈值），offset = 0.18 m。
  2. 障碍层：该体素是否被一个“真实的非地面障碍”膨胀覆盖（v288 起直接看膨胀贡献源）。
  3. 支撑层：脚下有没有可踩的面、是不是对的那一层、离台阶边缘多远、高度对不对（WrongHeight）、有没有悬空（SupportGap）。
  4. 新鲜度：点云和机身位姿都必须足够新，否则一律不放行。

输出一个“裁决”（verdict）：Free 才能走；其余（障碍、未知、高度不对、悬空、无效查询……）都拒绝。

⑥ 环境软代价场 ENV

Environmental Field（ENV225 格式）

局部层
人话：硬判定只会说“能/不能”，优化器需要知道“往哪边挪更安全”。ENV 是一张预先算好的“离台阶边缘还有多远、离墙还有多远”的地图，离得越近罚得越多，并给出往外推的方向（梯度）。
penalty_edge  = clamp((target − edge_margin) / target, 0, 1)        # v288：负余量饱和，梯度置 0
penalty_solid = max ((target − solid_margin) / target, 0)           # 实体墙：不设上限，穿透仍有推离梯度
cost          = penalty_edge² + penalty_solid² + 0.25 · terrain²
曲线代价       = Σ_span Σ_{3 个积分点}  cost(p(t)) · (interval / 3)    # v288：每段固定 3 点
代价权重
optimization.lambda_environment: 1.0（与 smooth/collision/fitness 同为 1.0，feasibility 0.1）
target
场文件内置的目标余量；审计里“额外余量”以 0.35 m 硬边界为零点，正值饱和于 +0.15 m
使用阶段
仅回弹（rebound）阶段；精修（refine）阶段不加环境项
源码
plan_env/src/environmental_field.cpp、bspline_opt/include/bspline_opt/environmental_curve_cost.h
注意：ENV 只是“软”的，它让曲线倾向远离危险；真正的安全由 ⑤ 的硬判定和 ⑧ 的终检保证。审计报告里 ENV 软余量与物理支撑余量分开报告，不能混为一谈。

⑧ 一次局部重规划流水线（核心算法）

SCANPlannerManager::reboundReplan（plan_manage/src/planner_manager.cpp）

局部层
人话：先随便找一条能过去的折线（种子），再把它变成一条光滑的曲线，用优化器把曲线“弹”离障碍；然后检查速度、加速度合不合规；最后用最新的地图把整条曲线逐点再查一遍，任何一步不过就不发布。
步骤做什么关键参数 / 失败日志
0 刷新输入refreshSensorInputs("replan_start")：从订阅队列手动取最新点云与位姿v31 引入；v288 回归点（见“线程与时间戳”）
1a 热启动种子如果上一条曲线还有效，直接截取剩余部分做种子（V48 warm start）日志 V48_WARM_SEED；失败则回退到图搜索
1b A* 种子dyn_a_star.cpp 地形感知 A*：端点先投影到支撑面；失败则退回上游弦线/平面候选；每条边都做碰撞查询reactive_stair_seed_search_failed；v288 端点调整/A* 失败均为 0
1c 捷径化若首尾直连无碰撞则只保留两点（OMPL reduceVertices 思路）verified_direct_seed_shortcut
2 拟合 B 样条按弧长每 0.2 m 取控制点（至少 7 个），三次 B 样条拟合并锁定起终点位置/速度/加速度（PVA）control_points_distance 0.2；spline_boundary_fit_failed
3 回弹优化L-BFGS 最小化：平滑 + 碰撞回弹（dist0 0.2）+ 可行性 + 环境 ENV；默认优化高度，失败后用固定高度模式再试一次mem 16、迭代 ≤200、g_eps 0.01；v288 加 past 3 / delta 1e-4；-1008 = 线搜索失败
4 时间重分配若超速/超加速度，按比例拉长时间并精修（平滑 + 贴合 + 可行性），最多 3 次；再强制最低巡航速度max_vel 1.0、max_acc 0.5、jerk 4.0、min_cruise_speed 0.6
5 边界与动力学检查重分配后端点 PVA 没漂；动力学可行final_spline_boundary_pva_rejected
6 终检 + 发布租约再次刷新输入，开启“发布租约”，以 0.05 m 步长对整条曲线逐点查双圆柱足迹（按预测朝向）final_spline_rejected；不过最多回到第 3 步再试 3 次
技术细节：失败时的三级退路
  1. 热启动被拒 → 清掉热启动，从同一 PVA 走完整图搜索链（V48_WARM_RESULT accepted=0 graph_fallback=1）。
  2. 三轴优化失败 → 关闭高度优化，固定高度重试（fixed_height_recovery_attempt），因为平滑可能把楼梯曲线“压低”到台阶里。
  3. 终检不过 → 把实际碰撞样本反馈给同一优化器，最多 3 轮（final_feedback_attempt）。

上游依据：SCAN-Planner @348e8a5（Apache-2.0），L-BFGS 实现对照 GCOPTER LBFGS-Lite。

技术细节：v288 对优化器的改动与它的问题
  • 线搜索失败（如 -1008）后，把求解器回滚的“最后接受点”写回控制点；若 iter_num_ > 1 且有限，就交给硬碰撞/动力学检查继续用。
  • 问题：iter_num_ 计的是函数评估次数，不是“已接受的下降步数”。初次评估 + 一次失败试探就满足 >1，此时可能一步都没走。
  • 按完成规划轮归一化，-1008 从 v287 的 5.04 次/百轮升到 11.71 次/百轮；绝对数下降（674→371）只是因为路线提前死掉，跑的轮数少了。

线程与时间戳：v288 为什么 6 条路线锁死

人话：v288 给地图加了一把锁，让各个回调排队，解决了 v287 的内存崩溃。但“排队”发生在消息已经被领走之后：拿着旧消息的线程在门外等，屋里的规划线程先拿了新消息登记；旧消息后进门，系统判“时间倒流”，而且一次倒流就把之后所有消息都拒掉。
证据值
regressed_body_source_stamp 日志命中v287：0 → v288：17 669
受影响路线A04、CU06、D07、CD12、CM02、CM07（GridMap 入口 4 条，FSM 入口 2 条）
零物理步复现调用冻结的真实 BodyTimeBuffer：push 返回 [1, 0, 0]（新消息接受、旧消息拒绝、之后更新的消息也被拒）
边界记录下来的传感器流本身是单调的；真实 DDS 的取消息顺序没有记录，不能当作已证实事实

验收体系怎么打分

第一关：50 + 3 离线门禁（不跑物理）

  • 50 个合法起终点 + 3 个非法对照，冻结后每个只调一次原生规划。
  • 通过线：合法 ≥ 48/50（96%）、非法 3/3 拒绝、合法已接纳例全局中位 ≤ 1.5 s。
  • 每条结果再做独立几何审计（实体面 + 原始点 + 支撑），所有起点要求额外余量 ≥ 0.10 m。

第二关：10 条固定路线，各跑一次物理

  • A04、G05、CU06、D07、S04、CD12、CM02、CM07、CS03、CE03。
  • 到达 + PD：原生判到达，且实测 PD 站稳。
  • 全记录几何：10 Hz 实测机身位姿下，支撑空隙、实体余量、原始点余量全部 ≥ 0（含终点收尾和 PD 尾段）。
  • 起立阶段单独审计（1 380 帧）。失败路线的“安全前缀”不算通过。
这是单次试验，不是统计可靠性；采样检查也不等于连续时间或足端接触认证。
