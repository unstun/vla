# Nav2 Foxy 完整接入：实现与验证

平台固定为 Ubuntu 20.04、ROS 2 Foxy、ARM64。Jetson 尚未连接；Dr Sun 将另行提供连接信息。本记录不包含真机运动。

## 已实现的软件链路

```text
NavigateToPose / 兼容的 HTTP 目标入口
  → Nav2 行为树
  → PCT 全局规划插件（原生 PCT）
  → 精确路线绑定
  → Nav2 ControllerServer + SCAN 控制器插件
  → 原有命令检查与实测停车证明
  → Lite3 仿真/行走接口
```

- Nav2 管理导航动作、执行和失败重试。发生失败时，先确认停稳，再重新规划。
- SCAN 保留三维建图、支撑判断和轨迹安全检查；地图层读取已完成的同一份三维地图，不另建第二套三维地图。
- 二维地图层提供身体高度附近的占用投影及新鲜度状态。楼梯支撑和完整轨迹碰撞仍由原生三维检查决定。
- 旧仿真的 `/goal`、`/cancel`、`/state` 接口转入 Nav2；保留原请求编号、地面目标到机身目标的转换，以及初始全局路线末段朝向/显式朝向覆盖。
- Foxy 导航动作放在 `/nav2_internal` 命名空间，公开入口由停车网关提供。原有带身份的命令输出补丁继续保留。

## 建图对照

使用同一批原始 188 帧输入，按 10 Hz 回放。下列年龄是观测者持有地图的采样年龄，不是实体控制延迟。

| 条件 | 实际融合 / 丢弃 | 最大采样地图年龄 | 超过 250 ms 的样本 |
|---|---:|---:|---:|
| FIFO，正常负载 | 188 / 0 | 100 ms | 0 |
| Nav2 式窗口，5 Hz 调度 | 188 / 0 | 400 ms | 73 |
| Nav2 式窗口，20 Hz 调度 | 188 / 0 | 100 ms | 0 |
| 20 Hz，另行注入两次 650 ms 卡顿 | 188 / 0 | 800 ms | 15 |

四组最终三维地图状态和占用数组字节完全一致。选用 20 Hz 调度、0.5 秒观测窗口；雷达输入仍是 10 Hz。这个结果支持修正调度配置，不能证明完整行走已经达到 30 Hz，也不能把旧 Mac/x86 仿真的耗时全归因于 FIFO。

v98 最后的 Linux 状态文件比最后收到的确认更新，回传哈希核对失败。两边
原始字节和超时记录均保留；这次不能算完整的运行证据链通过，也没有到达、
连续行走或稳定 30 Hz 结果。v95–v97 的状态回传核对通过。

## 已修复的问题和仍待定位的问题

- 动作请求的通信确认期限与实际传感器年龄分开配置。
- 未生成第一条轨迹时重复取消，控制器仍回应“输出已撤销”；实测停稳继续
  由应用状态判断，不能用这个确认直接宣告停稳。
- 精确同一时间戳曾因 `sec + 1e-9 * nanosec` 与 ROS 的换算顺序不同而产生
  舍入误差。用捕获的 19.940670013 秒时间复现失败，再用统一换算验证修复。
- 原场景仍出现局部种子搜索/轨迹安全拒绝。日志还显示原生规划线程手动读取
  的机身时间领先该线程处理到的仿真时钟 10–95 ms；这是下一步隔离检查的
  线索，尚不能把所有拒绝归因于它。
- v98 状态通道超时需要独立复现。没有扩大通信超时或放宽安全检查来掩盖失败。
