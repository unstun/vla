## Condition configs

`EXP/public_scenes/configs/vln_cam_<cond>.yaml`, generated by
`REQ/make_condition_yamls.py` from `REQ/conditions.json` (the single source of
the condition table) as text substitutions on `vln_public_scenes.yaml`, with
exactly these keys changed under `habitat.simulator` (`hfov` is an integer
field in Habitat's structured config):

| cond | `rgb_sensor`/`depth_sensor.position` | `.orientation` (rad) | `.hfov` | `tilt_angle` |
| --- | --- | --- | --- | --- |
| `c1_lite3_rig` | [0.0, 0.42, -0.25] | [-0.349066, 0, 0] | 54 | 0 |
| `c2_height_only` | [0.0, 0.42, -0.25] | [0, 0, 0] | 79 | 15 |
| `c3_fov_only` | [0.0, 1.25, 0.0] | [0, 0, 0] | 54 | 15 |
| `c4_raised_mount` | [0.0, 0.65, -0.25] | [-0.261799, 0, 0] | 54 | 0 |

Habitat's agent frame has -z forward, so the forward offset is a negative z.
RGB and depth sensors always receive identical position, orientation, and hfov
so the System-1 RGB-D pair stays aligned. `width`/`height`, `min_depth`/
`max_depth`, actions, measurements, and dataset paths stay byte-identical to
the baseline YAML. A diff of each condition YAML against the baseline YAML is
recorded in `REQ/provenance.json` and must show only the listed keys.

`EXP/public_scenes/configs/habitat_dual_system_cam_cfg.py`: derived from
`habitat_dual_system_public_cfg.py` with two changes: `config_path` comes from
the environment variable `CAM_YAML`, and `RUN_DIR` from `CAM_RUN_DIR`. All
model settings stay identical (`dual_system`, `checkpoints/InternVLA-N1-DualVLN`,
`num_history` 8, 384x384 resize, 1024 tokens, `vis_debug` True, `save_video`
True, 500 steps). The evaluator resolves resolution and hfov from the YAML, and
in `dual_system` mode uses no intrinsic or camera transform, so no model-side
camera setting needs to change.

## Preflight (`REQ/preflight_cam.py`)

Runs from the launch directory `EXP/work/InternNav` in `official_env_024`, once
per condition, writing `REQ/preflight/<cond>.json` and PNGs. Stages, each
recorded with pass/fail and stopping at the first failure:

1. `versions`: habitat-lab 0.2.4, habitat-sim 0.3.3, torch, transformers.
2. `paths_and_links`: YAML, cfg, annotation, scene, navmesh, both checkpoints
   resolve from the launch directory.
3. `evaluator_identity`: SHA-256 of `habitat_vln_evaluator.py`,
   `scripts/eval/eval.py`, `vln_utils.py`, scene, navmesh equal the values in
   `EXP/public_scenes/runs/public_eval_v5/inputs.json`.
4. `composed_config`: compose the Hydra config through the same
   `get_habitat_config` call the official evaluator uses; assert resolved
   `position`, `orientation`, `hfov` for both sensors and `tilt_angle` equal
   the condition spec; assert `width`/`height` 640x480.
5. `render_start_frame`: open `habitat.Env`, reset to episode 1, save RGB PNG
   and a depth PNG, and compute the 90th percentile of metric depth over the
   bottom 16 image rows in the central 200 columns (p90 rather than the
   median so a near obstacle cannot mask the floor). Habitat depth is z-depth
   along the optical axis, so the expectation is built per row as
   h / (sin p + tan(theta_r) cos p) over the same block and percentile, not
   the ground distance h / tan(p + VFOV/2); the two agree only for a level
   camera. Flat-floor expectation at zero floor gap: 0.62 m (C1), 0.72 m (C2),
   3.48 m (C3), 1.07 m (C4). Because z-depth scales linearly with height for
   a flat floor at fixed pitch and rows, the measurement is converted to an
   implied agent-origin-to-floor gap, h * (measured / expected - 1), which
   must lie within -0.05 to 0.30 m (round-1 measurements: 0.158 to 0.163 m
   for all four conditions, a navmesh property of this start pose). The
   original 25 percent ratio test is recorded but no longer fails the stage.
   The stage also reads the simulator's own sensor state
   and asserts the sensor height above the agent, the forward offset, and the
   pitch of the sensor forward vector, so the orientation sign is verified
   directly as well. Also record the median depth of the top 16 rows. This
   catches a wrong height, a wrong pitch sign, or an ignored orientation key
   without relying on the unverified radian convention.
6. `tilt_noop`: step LOOKDOWN once and LOOKUP once and read the sensor pitch
   before and after. With `tilt_angle: 0` the pitch delta must stay within
   0.01 degrees and at most 1 percent of pixels may change (round 2 showed a
   zero-amount look_down re-normalises the sensor quaternion by 1 to 2 ULP,
   flipping 0.31 percent of edge pixels with the camera unmoved, so a
   bit-identical test is wrong); with non-zero tilt the pitch delta must equal
   the tilt and at least 5 percent of pixels must change.
7. `gpu_budget`: the preflight closes its own simulator first, then requires
   free memory reported by `nvidia-smi` to be at least the maximum
   `memory.used` delta seen in the baseline's `gpu_samples_every_5s.csv`
   (about 19.5 GB against a 24 GB device shared with Isaac Sim); records the
   resident processes without touching them.

The lead inspects the four RGB PNGs before accepting AC2.

## Launcher and matrix

`REQ/run_cam_eval.sh <cond> <run_id>`: derived from
`public_scenes/scripts/run_public_eval.sh`. Refuses if the run directory
exists, if `REQ/preflight/<cond>.json` is missing or not passed, or if any
required file is missing from the launch directory. Writes `inputs.json` with
the same hash list as the baseline plus the condition name, the YAML hash, and
the resolved camera geometry (copied from the preflight JSON). Launches
`python scripts/eval/eval.py --config public_scenes/configs/habitat_dual_system_cam_cfg.py`
with `CAM_YAML`, `CAM_RUN_DIR`, `MAGNUM_LOG=quiet`, `HABITAT_SIM_LOG=quiet`,
samples `nvidia-smi` every 5 s, and writes `exit.json`.

`REQ/run_matrix.sh`: for cond in c1..c4, for k in 1..5:
`python3 scripts/run_job.py --seconds 1800 cam_<cond>_v<k> -- bash REQ/run_cam_eval.sh <cond> cam_<cond>_v<k>`.
Skips run ids that already exist, never stops the matrix on a failed run, and
appends one line per run to `REQ/matrix_log.jsonl` (run id, exit code,
timed_out, wall seconds). Order is condition-major so a partial return still
yields complete conditions.

Budget: 20 runs, each at most 1,800 s; the baseline averaged 144 s per run
plus model load, so about one GPU hour is expected and 10 hours is the hard
ceiling.

## Analysis (`REQ/summarise_conditions.py`)

Reads every `EXP/public_scenes/runs/*/progress.json`, `result.json`, and
`trace_0/*.jsonl`; groups runs into B0 (`public_eval_v1..v5`) and the four
`cam_*` prefixes; emits `REQ/condition_summary.json` and
`REQ/condition_summary.md` with, per condition and per episode: successes out
of runs, navigation error min/median/max, oracle success, SPL mean, steps,
collision count, STOP provenance (learned S2 STOP, fallback, step cap, deadline),
System-2 branch counts, pixel-goal counts. B0 numbers must reproduce the
review's 3/5 and 2/5 before the new conditions are reported. The existing
`summarise_runs.py` is left untouched.

## Evidence and Sync Gate

- Author locally, verify YAML parse and Python compile locally, record SHA-256
  of every authored file in `REQ/provenance.json`.
- Executor syncs `REQ/` and the five config files to the remote copy, verifies
  hashes, runs preflight, then the matrix, then the summariser, then ffprobe
  frame counts for every MP4.
- Return everything under `EXP/public_scenes/runs/cam_*`, `EXP/runs/cam_*`,
  and `REQ/` to the same local relative paths; `REQ/manifest.sha256` is
  generated remotely after the last evidence edit, excludes itself and
  `OPUS_RETURN.md` (written afterwards), and is verified locally with
  `shasum -a 256 -c`.
- `REQ/OPUS_RETURN.md` in English; task stays at `review` until the lead
  accepts; nothing staged or committed by the executor.

## Risks and mitigations

- Orientation sign or units wrong: caught by preflight stage 5 before any run.
- `tilt_angle: 0` rejected or non-zero in effect: stage 6 fails; fallback is a
  separate action-space config with the look actions removed, which requires a
  lead decision because the evaluator calls LOOKDOWN unconditionally.
- Depth values at HFOV 54: the evaluator scales depth by `max_depth`; the
  YAML keeps 0 to 10 m so the scaling is unchanged.
- Shared GPU: stage 7 plus per-run sampling; the matrix stops only if a run
  cannot allocate memory twice in a row.
- Unseeded System 1: five runs per condition as in the baseline; the summary
  reports ranges, not means alone, and the claim boundary is explicit.
- The `look_down_followup` branch sees the same frame as the level view in C1
  and C4; this mirrors the real-world agent and is recorded as a protocol
  difference, not corrected.

## Rollback

Nothing destructive is performed. New run ids only; if a condition must be
re-specified, a new condition name is used and the old runs are kept as
evidence of the abandoned specification.

## Round 4: head-camera proxy conditions (2026-09-10)

Rendering stays the evaluation camera (HFOV 79, 640x480) because the
deployment adapter will centre-crop the head camera's 1280x720 stream
(fx 508.7 from the third-party calibration) to 839x629 px, which is HFOV 79
at 4:3 with VFOV 64.9 deg against the simulator's 63.5 deg. Only the sensor
position `[0, 0.40, -0.27]`, orientation (0 or -15 deg pitch on x), and
`tilt_angle: 0` differ from B0, so the existing generator, preflight, launcher,
matrix, and summariser apply unchanged; `conditions.json` gains the two
conditions and a `round4` execution record, `run_matrix.sh` lists them in its
default set, and `record_provenance.py` covers the two new YAMLs. Preflight
expectations follow C2 (level, 0.42 m) for C5 and C4 (15 deg down, tilt 0) for
C6. No crop is simulated; the adapter's crop is a deployment-side contract
recorded in the research note (6b) and to be validated with real frames later.

## Round 5: fused virtual camera (2026-09-11)

Geometry (Habitat agent frame, y up, z back; orientation[0] = pitch, + up, sign verified by round-1 renders): virtual `rgb_sensor`
and `depth_sensor` at (0, 0.40, -0.27), level, 640x480, HFOV 79; `fused_head_rgb_sensor` same position, +0.29147 rad, 1280x720,
HFOV 105; `fused_d435_rgb_sensor` / `fused_d435_depth_sensor` at (0, 0.42, -0.25), -0.34907 rad, 640x480 HFOV 54.6 (c7) or
1280x720 HFOV 69 (c8), depth min 0 max 10 unnormalised.

Fusion (`fused_camera.py`, numpy, OpenCV optional): head by rotation-only lookup table (bilinear); D435i by back-projection of its
z-depth, transform to the virtual frame, z-buffered splat, two passes of 3x3 hole filling; composition head > 8-row feather > D435i >
black; coverage map returned. Verified by an exact analytic-scene self-test.

Integration (`fused_camera_plugin.py`): habitat-lab 0.2.4 ConfigStore nodes (sim sensors without package, lab sensor with package
`habitat.task.lab_sensors.fused_rgb_sensor`), sensor classes registered via `registry.register_sensor`, uuids from config; the task
sensor reads the three sim sensors' configs from `sim.habitat_config` and overrides `rgb` because EmbodiedTask.reset/step merge task
observations over sim observations. Import hook: the run config file (`habitat_dual_system_fused_cfg.py`), executed by eval.py before
Evaluator.init. The sim `rgb_sensor` stays because the evaluator reads its position, and it provides the ideal reference.

Trade-offs: the evaluator's `depth` is ideal (unused by nextdit_async System 1); black corners and seams are deliberately left in
(deployment-faithful); a 15-deg-down virtual camera is not attempted (its bottom 14 % would be blank). Rollback: conditions c1-c6 and
their config path are untouched; the per-condition eval_config lookup falls back to the camera config.
